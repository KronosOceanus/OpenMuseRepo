# OpenMuse

**让乐谱可以 fork 和合并。**

同一个曲子常被不同的人扒，每份都各有几处错。现在没有好办法把这些改进汇总起来 ——
MuseScore 上的扒谱是各自独立的文件，社区仓库（比如 OpenScore）是单向镜像，没人提 PR。

这个仓库把 **git 的协作模型** 搬到乐谱上。它的关键是补上 git 缺的那一块：
**代码有测试，音乐没有。**

---

## 核心：让 `.mscx` 可 diff

`git diff` 直接用在 MuseScore 文件上是废的。实测（`神话2.mscz`，4074 行）：

```
<eid> 798 个                     ← 随机元素 ID，占 19.6% 的行
只改 eid 的值    → diff 1596 行   ← 全是噪音
剥掉 eid         → diff    0 行   ← 噪声清零
剥掉 eid 再改个音 → diff    2 行   ← 精确到 <pitch>
```

**所以第一步只是剥掉 `<eid>`。** 剥完之后，`.mscx` 是一个正常的、可以逐行 diff 的文本文件。

> MuseScore 官方手册把 `.mscx` 定义为「未压缩格式，主要用于调试或**存储在版本控制系统中**」。
> 同一个曲子的 `.mscz` 只是它的 zip 包装。

## 第二步：按**小节**而非按行

行级 diff 的粒度对乐谱是错的 —— 一个 `<Measure>` 展开成几十行，
「第 21 小节改了」这件事在行级 diff 里看不出来。

`score-diff.mjs` 按小节对齐比较，输出的是：

```
小节 21（谱表 1）
  - <pitch>71</pitch>
  + <pitch>74</pitch>
```

**这才是能拿去裁决的单位** —— 一个改动 = 一个小节里的一处差异。

## 第三步：只渲染改动的小节

MuseScore 的 CLI 只能整份导出（`--page` 能筛页，不能筛小节）。
办法是**先把其余小节从 XML 里剔掉，再交给 MuseScore** ——
筛完之后的乐谱只有那几个小节，导出的图和音频自然就只有那几个小节。

实测：整份 101898 字节 → 筛出 1 个小节后 5367 字节（**保留 5%**），
渲染出 1329×840 的紧凑谱面图 + 5 秒音频。

## 第四步：**用乐谱表达差异**，而不是用文字

文字 diff 是给程序员看的。审一份扒谱要判断的是「**这一处对不对**」，
而乐谱的差异用乐谱表达最直接。

`compare.mjs` 把两个版本**摞成一份乐谱**（上半原版、下半改后），
同一拍落在同一水平位置，**差异自己就跳出来了** —— 不用加任何标记，也不用读数字：

```
┌─ 原版 ──────────────┐
│  ♪  ♪  ♪  ♪  𝄾      │   第 1 个音在五线谱内
│  ♪  𝄾  𝄾            │
├─ 改后 ──────────────┤
│  ♪  ♪  ♪  ♪  𝄾      │   第 1 个音高到谱线上方
│  ♪  𝄾  𝄾            │
└─────────────────────┘
```

实现上是纯结构操作，不碰任何格式语义：
1. 复制一份 `<Part>` 声明给版本 B
2. 把 B 的音乐 `<Staff>` 接在后面，**id 重编号**
3. 改掉两边的 `<longName>` / `<shortName>` / `<trackName>`，谱面上显示「原版 40–41」「改后 40–41」

### 按「连续段」切分

最初的实现是把**所有**改动的小节筛出来拼成一份对照谱。实测（改了 5,6,7,8, 20,21,22, 40,41）发现三个问题：

| 问题 | 表现 |
|---|---|
| **非连续小节被首尾拼在一起** | 读起来像一段连贯的音乐 —— **这是误导** |
| **分页把上下对照劈开** | 跨页之后「上原版 / 下改后」的对应关系就断了 |
| **显示名退化** | `longName` 只在第一个系统用，后续系统只剩简称 |

所以改成**按连续段切**：

```
改动 5,6,7,8, 20,21,22, 40,41
        ↓
第 5–8 小节  → compare-1.mscx + compare-1.png
第 20–22 小节 → compare-2.mscx + compare-2.png
第 40–41 小节 → compare-3.mscx + compare-3.png
```

四件事一起解决：每段内部连续、每张图都很短（一页装得下）、标签自带小节范围、
改动多的时候是一列小图而不是一张长图。

两条保险：
- **单段超过 8 小节**就再切一刀（`--max-per-run`）
- **段数超过 6** 就只渲染前 6 段（`--max-runs`），剩下的写一句说明

**所以 PR 报告是「改动 N 小节 → M 张对照图」**，文字 diff 退到折叠块里。

> ⚠️ **已知瑕疵：图里上下两组的间距偏大。**
> 原因是 `.mscx` **带不了页面布局** —— 页面样式在 `.mscz` 里的 `score_style.mss`，
> 往 `.mscx` 塞 `<Style>` 块会被 MuseScore 忽略（三种位置和单位都试过）。
> 所以渲染出来是 A4 版式，内容少的时候留白多。图仍然可读，只是不够紧凑。

## 用法

### 生成对照谱（推荐）

```bash
node scripts/compare.mjs 原版.mscx 改后.mscx out/ --labels 原版,改后
```

输出是**一个目录**，里面按连续段分成 `compare-1.mscx`、`compare-2.mscx`…
每份都是「上半原版、下半改后」，而且**只含那一段的小节**，不是整份。

用 MuseScore 打开，或渲染成图：

```bash
for f in out/compare-*.mscx; do
  "/Applications/MuseScore 4.app/Contents/MacOS/mscore" -o "${f%.mscx}.png" -T 20 "$f"
done
```

### 收一首曲子进来

```bash
node scripts/import-score.mjs ~/我的谱子.mscz 曲名
```

产出：

```
pieces/曲名/
├── score.mscx      ← 剥过 eid，参与 diff（这份进 git）
└── source.mscz     ← 原始文件（存档，不参与 diff）
```

### 看改动

```bash
node scripts/score-diff.mjs pieces/曲名/score.mscx 改过的.mscx
```

### 生成对照（谱面图 + 音频）

```bash
node scripts/render-changed.mjs 基准.mscx 提交.mscx out/
```

产出 `out/before.png` `out/before.mp3` `out/after.png` `out/after.mp3`。

### 在 CI 里（自动）

`.github/workflows/score-preview.yml` 会在有人提 PR 时自动跑完上面全部，
把结果当评论贴回 PR。**审核的人不用开 MuseScore、不用自己找位置** ——
PR 里直接看到**对照谱图**，文字 diff 收在折叠块里。

> ⚠️ **已知缺陷：PR 评论里的图暂时显示不出来。**
> 报告里写的是 `![对照谱](神话2/compare-1.png)`，但 `out/` 不在仓库里，
> GitHub 渲染不了。图和音频目前作为 **artifact** 上传，要点进去下载。
> 修法是把预览图提交到一个 `previews` 分支、用 raw URL 引用 —— 还没做。

## 文件

```
scripts/
  normalize.mjs        剥 eid（核心，其余都依赖它）
  score-diff.mjs       按小节的语义 diff + 小节字符区间定位 + 筛小节
  merge-versions.mjs   两份乐谱摞成一份（Part 复制 + 谱表重编号 + 改显示名）
  compare.mjs          差异 → 按连续段切分 → 每段一份对照谱
  render-changed.mjs   筛出改动小节 → 渲染 PNG / MP3
  import-score.mjs     把 .mscz 收进仓库
  ci-preview.mjs       CI 入口：扫改动 → 出对照谱图 → 写报告
  selftest.mjs         自测（验证 diff 报的小节号真的是改的那个）
.github/workflows/
  score-preview.yml    PR 时自动生成对照
.gitattributes         *.mscx text ← 这一行是关键
```

## 踩过的坑（都写在代码注释里了）

| 坑 | 表现 | 处理 |
|---|---|---|
| **`<eid>` 噪音** | 同一曲子两次导出差 1596 行 | 剥掉，只此一招 |
| **开闭标签缩进不一致** | `<Staff id="1">` 缩进 4，`</Staff>` 缩进 6 | 靠开标签位置切段，不依赖闭合标签 |
| **按 (谱表, 小节) 筛会产出非法乐谱** | 谱表2 变成零小节，MuseScore 拒收 | 按**小节序号**筛，所有谱表保留相同序号 |
| **靠缩进区分两类 `<Staff>`** | 拼错一格 → 解析全崩，报「0 个谱表」 | 改判「是否落在某个 `<Part>…</Part>` 区间内」 |
| **段尾取了下一个开标签的结束位置** | 下一个 `<Staff>` 被算进上一段 → 重复标签 → 拒收 | 取下一个开标签的**起始**位置 |
| **PNG 文件名带页码后缀** | 要 `out.png`，拿到 `out-1.png` | 导出后回头找实际文件名 |
| **PNG 满页留白** | 一小节铺在整张 A4 上 | `-T 20` 裁掉 |
| **macOS 沙箱** | MuseScore 静默无产出（退出码还是 0） | 它要写 `~/Library/Application Support/MuseScore/`；CI 上无此限制 |

## 三个它**不**解决的问题

**① 版权。** 这个仓库只提供工具，不托管内容。**但工具不改变内容本身的合法性。**

按《著作权法》第 24 条，「为个人学习、研究或者欣赏」可以构成合理使用 ——
但司法实践看的是**传播范围**：

> 如果相关作品的传播范围较广，例如导致其向不特定的公众公开，
> 则已经明显超出"为个人"的范畴，不构成合理使用。

而且完整扒谱会「完整呈现权利作品的内容」，本身就过不了「不影响该作品的正常使用」。
**「不售卖」也不构成抗辩** —— 是否营利并非要件。

**所以这个仓库适合的初始内容是：公有领域作品、你自己的原创、或已获授权的作品。**
（OpenScore 只做古典，很可能不是偏好，是策略。）

**② 「谁对」仍然是主观判断。** 这个仓库能把判断成本降下来（不用开软件、不用找位置），
但不能消除它 —— 音乐没有测试。真正能改变这一点的，是**音频对齐**
（把改动的小节和原曲录音对齐播放），那是下一步。

**③ 冷启动。** 没人来，就没人提 PR。这是社交问题，不是技术问题。

## 跑自测

```bash
node selftest.mjs
```

会造一个"改了谱表1 第21小节的一个音"的副本，验证 diff 报出的小节号
确实就是被改的那一个 —— 而不是碰巧对上。
